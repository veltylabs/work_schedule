# work-schedule Architecture

## 1. Domain Scope
Provides a read-only view of the weekly work schedule for clinic staff (doctors, nurses, etc.).
Reads from two legacy tables maintained by an external system — this module never owns or migrates
their schema.

## 2. Core Entities
- **Staff:** The clinic employee. `password_hash` is excluded from the ORM codec/DB scan via
  `model.Field{Exclude: true}` — it still exists on the generated `Staff` struct (for whatever
  side channel manages it), but `ormc`-generated `Pointers()`/`EncodeFields`/`DecodeFields` never
  touch it.
- **WorkCalendar:** One row per staff member per working day. `is_active = false` indicates
  a non-working day; `start_time`/`end_time` are meaningful only when `is_active = true`.

## 3. Architectural Patterns
This module is coupled only to published contracts, not to concrete infrastructure — see
`AGENTS.md` (this repo's root) for the full whitelist/blacklist. Applied here:

1. **Read-Only / No DDL:** `New(db *orm.DB) *Module` never calls `ddl.CreateTable`/`ddl.Sync` (or the
   removed `orm.DB.CreateTable`) for `Staff`/`WorkCalendar`. Tables are managed entirely by the
   legacy system. This is the one module in the `veltylabs/modules/*` batch where "the module owns
   its own schema migration" does **not** apply — the schema belongs to someone else. `New()` is
   side-effect free apart from storing the `*orm.DB` reference.
2. **Dependency Injection, no `Deps`:** `New(db *orm.DB) *Module` takes only the already-connected
   `*orm.DB`. Unlike most modules in this ecosystem, this one declares no `Deps{IDs, Publisher}` —
   it mints no IDs (it never constructs a `Staff`/`WorkCalendar` row) and publishes no events (a
   read has nothing to announce). Do not add either speculatively.
3. **Transport — `router.OpModule`:** `ModelName() string` + `MountOps(reg router.OpRegistry)`
   register the module's one operation with `.Requires(resource, action)` + `.Accepts(&ArgsType{})`.
   The module never implements `router.APIModule`/`Router`, and never imports `tinywasm/mcp` — the
   app decides which transport (`mcp.HarvestOps`, or any future one) harvests the op.
4. **No `view.Presenter`:** `get_work_schedule` is a single detail lookup keyed by `staff_id`,
   returning one nested composite value — not a list of selectable records. It does not fit
   `view.New`'s list/select/save/delete shape (no `OpList*`, nothing to save or delete), so this
   module declares no `NewView`.
5. **Encoding-agnostic:** the request/response structs (`GetWorkScheduleArgs`, `ScheduleEntry`,
   `StaffResponse`) implement `model.Encodable`/`Decodable` (generated by `ormc`); `router.Context.
   Decode`/`Encode` walk that interface with whatever concrete codec the transport installs. The
   module never imports `tinywasm/json` directly.

## 4. Ops (via `MountOps`)
| Op | Action | Resource | Params | Returns |
|----|--------|----------|--------|---------|
| `get_work_schedule` | `r` | `work_schedule` | `staff_id` (int) | `staff_name`, `staff_role`, `schedule[]` (`day`, `day_name`, `is_active`, `start`, `end`) |

Spanish day names: Domingo, Lunes, Martes, Miércoles, Jueves, Viernes, Sábado.
`start`/`end` fields are omitted when `is_active = false`.

## 5. Composition Root Example
```go
sched := workschedule.New(db) // *orm.DB — no Deps, no schema migration
sched.MountOps(opRegistry)    // router.OpRegistry
// No sched.NewView(...): this module has no Presenter (see §3.4).
```

## 6. Schema
See [`docs/diagrams/database.md`](diagrams/database.md). Both `staff` and `workcalendar` are legacy
